## What Is AEGIS?

AEGIS (AI-powered Enterprise Governance & Intelligence for Support) automate support workflows end-to-end. Every feature maps directly to the Support Business domain.

| AEGIS Feature |
|---|---|
| Chatbot Development | Streaming RAG chatbot with FAISS KB, confidence gating, CSAT |
| LLM Workflow Automation | 5-layer intent router — escalation → greeting → rules → FAISS → LLM |
| Knowledge Base Development | 10 Commvault KB documents, chunked, embedded, indexed with FAISS |
| Ticketing Automation | Auto-classification, SLA tracking, priority assignment, team routing |
| Email Automation | Real Gmail IMAP/SMTP integration, intent-based auto-response pipeline |
| Automated Reporting | Analytics dashboard — volume trends, KB gap detection, CSAT distribution |
| REST API Integration | Groq API, Gmail IMAP/SMTP API, FastAPI-ready backend architecture |
| CRM Integration | SQLite with 5 tables — tickets, events, email logs, CSAT, KB gaps |

## 7-Page Application

### Dashboard
Real-time operations overview. 6 KPI cards (automation rate, escalation rate, resolution rate, avg CSAT, KB confidence). Plotly ticket volume trend chart (total vs bot-resolved vs escalated). SLA status table for all open tickets. P1 alert banner. KB coverage gap panel.

### Chatbot
Streaming RAG chatbot powered by Groq Llama 3.3 70B. Responses stream token-by-token in real time. Source document chips show which KB files backed each answer. Confidence bar shows retrieval quality (green/amber/red). 5-star CSAT rating after each response. Follow-up question suggestions generated by LLM. 4 response paths: greeting → RAG answer → general conversation → escalation with ticket card.

### Ticket Inbox
Every chatbot escalation and processed email auto-creates a ticket. Multi-filter view (status/priority/intent/search). Inline editing — change status, priority, add resolution note. SLA countdown per ticket (P1=4h, P2=24h, P3=72h, P4=168h). Auto-generate KB article from any resolved ticket.

### Email Automation Hub
5 tabs covering the full email pipeline:
- **Live Inbox** — Fetch real unread Gmail via IMAP, classify, process, send SMTP response
- **Process Email** — Manual form with 8 quick-test buttons for every scenario
- **Batch Simulation** — Simulate 5–100 emails, measure automation rate
- **Email Log** — Full audit trail of every processed email, export to CSV
- **Email Setup** — Configure IMAP/SMTP with live connection testing

### Analytics
4-tab intelligence dashboard. Volume & trends, intent breakdown, CSAT distribution, KB gap report. Confidence trend line with escalation threshold marker. KB gap report shows exactly which topics need more documentation.

### Knowledge Base Admin
Browse all 10 KB documents. Upload new .txt/.md files — indexed into FAISS immediately without rebuild. Test Retrieval tab — type any query and see confidence score, source documents, and full response. Batch coverage test runs 10 standard queries and shows pass/fail table.

### Settings
Runtime configuration without touching code. Confidence threshold slider (0.10–0.80). Model selector. Max tokens and top-k controls. Live YAML editor for routing rules. SLA threshold customisation per priority level.

## Architecture

```
User input
    │
    ▼
classify(text) ──── 5-layer router ────────────────────────────────┐
    │                                                               │
    │  Layer 1: GREETINGS set + GREETING_PHRASES list              │
    │  Layer 2: ESCALATE_PATTERNS regex (hard escalation)          │
    │  Layer 3: RULE_PATTERNS regex (12 intents, 90% of traffic)   │
    │  Layer 4: FAISS similarity search (confidence >= 0.35)       │
    │  Layer 5: Groq LLM (general conversation, temp=0.7)          │
    │                                                               │
    ▼                                                               │
stream_rag_query()                                              _escalate
    │                                                               │
    ├── FAISS.similarity_search_with_score(k=5)               save_ticket()
    │                                                               │
    ├── _compute_confidence()                               ticket card in chat
    │   → 1.0 - (avg_L2_distance / 2.0)
    │
    ├── conf >= 0.35 ──→ SYSTEM_PROMPT + context ──→ Groq stream
    │                                                    │
    │                                             st.write_stream()
    │                                             source chips
    │                                             confidence bar
    │                                             CSAT stars
    │                                             follow-up suggestions
    │
    └── conf < 0.35 ──→ intent == general_inquiry ──→ Groq conversational
                    └──→ intent == support         ──→ escalate + save_ticket()
    │
    ▼
save_event() ──→ SQLite events table
```

## Intent Classification — 5-Layer Router

```python
def classify(text: str) -> tuple[str, bool]:
    t = text.lower().strip()

    # Layer 1: Greeting detection — O(1) set lookup, free
    if t in GREETINGS:                          return "_greeting", False
    if any(p in t for p in GREETING_PHRASES):   return "_greeting", False

    # Layer 2: Hard escalation — regex, must-escalate phrases
    # "speak to human", "production down", "data loss", "lawsuit"
    for pat in ESCALATE_PATTERNS:
        if re.search(pat, t):                   return "_escalate", True

    # Layer 3: Intent rules — 12 regex patterns, ~90% of support traffic
    # "backup.*fail", "CV-[0-9]+", "restore", "licens", "login"
    for pattern, intent, _ in RULE_PATTERNS:
        if re.search(pattern, t):               return intent, False

    # Layer 4+5: FAISS + Groq (handled in rag_query)
    return "general_inquiry", False
```

**12 intents covered:**
`backup_failure` · `restore_request` · `licensing` · `access_issue` · `performance` · `installation` · `configuration` · `billing` · `feature_request` · `general_inquiry` · `_greeting` · `_escalate`

```sql
-- 5 tables, all auto-created on first run by init_db()

tickets          -- id, subject, body, intent, priority, team, status, source,
```

## Production Upgrade Path

The `docker-compose.yaml` and `backend/` directory contain the full production architecture:

```bash
# Spin up the full production stack
docker-compose up -d

# Services:
# api        → FastAPI on port 8000
# postgres   → PostgreSQL 15 on port 5432
# redis      → Redis 7 on port 6379
# scheduler  → APScheduler background jobs (SLA reminders, reporting)
```

**To scale from prototype to production:**
- Replace SQLite → PostgreSQL (connection string in `.env`)
- Add Redis for session state across workers
- Deploy FastAPI backend on Railway using `railway.toml`
- Use APScheduler for automated SLA reminder emails
- Replace FAISS with Pinecone for multi-user shared KB index
